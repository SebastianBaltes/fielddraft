Noch eine Idee für FieldDraft: Man kann die generierten Three 3D-Assemblies direkt online publishen und per URL oder IFrame einbinden.

Das ist eine hervorragende Ergänzung zur strategischen Ausrichtung von FieldDraft, insbesondere im Hinblick auf Phase 3 der Roadmap (Interaktions-Export). Die Idee, 3D-Assemblies direkt per URL oder IFrame zu publizieren, verwandelt das Tool von einer reinen Konstruktionsumgebung in eine Publishing-Plattform für Hardware-Dokumentation.

Hier ist die Analyse, wie sich dieses Feature nahtlos in die bestehende Architektur einfügt:

1. Technischer Enabler: Die R3F-Architektur
Da FieldDraft im Frontend bereits auf React Three Fiber (R3F) setzt, ist der Weg zu einem Web-Viewer extrem kurz:

Komponentenzugriff: Da das Modell im Editor bereits als Baum von R3F-Komponenten existiert, muss für den Viewer lediglich eine "Read-Only"-Version der Viewport-Komponente gerendert werden.

Performance: Durch die Multi-Body-Isolation und den Verzicht auf globales Echtzeit-Raymarching im Viewport sind die eingebetteten Modelle leichtgewichtig genug, um auch in Blogposts oder Dokumentationsseiten flüssig zu laufen.

2. Umsetzung: Der "Shareable" Workflow
Ein "Publish"-Feature könnte wie folgt funktionieren:

Snapshot-Generierung: Der User klickt auf "Publish". Das System erstellt einen permanenten JSON-Snapshot des Projekts in der MariaDB.

Statische Hosting-URL: Es wird eine eindeutige URL generiert (z. B. fielddraft.io/v/projekt-id).

IFrame-Snippet: FieldDraft liefert einen fertigen Code-Block:
<iframe src="https://fielddraft.io/v/123" width="600" height="400"></iframe>

3. Synergie mit der Kinematik (Phase 3)
Die Einbettung wird besonders mächtig, wenn die in Meilenstein P1 bis P3 geplanten Features hinzukommen:

Interaktive Dokumentation: Anstatt einer statischen STL-Vorschau können Nutzer die Mates und Gelenke (Joints) direkt im IFrame bewegen.

Leichtbau-Viewer: Da der Viewer keinen schweren Geometrie-Kernel zum Editieren laden muss (WASM-Payload), bleibt die Ladezeit für den Endnutzer gering.

4. Strategischer Vorteil für Startups
Für die Zielgruppe der Hardware-Startups bietet dies einen massiven Mehrwert:

Pitch-Decks: Interaktive 3D-Modelle des Prototyps direkt im Browser verlinken.

Montageanleitungen: Kunden können das Bauteil online drehen, wenden und mechanische Funktionen testen, ohne CAD-Software installieren zu müssen.

Transparenz: Da die Datenhoheit gewahrt bleibt (Sichtbarkeit einstellbar), können Firmen entscheiden, ob sie nur das Mesh oder die volle parametrische Historie teilen.

Einordnung in die Roadmap
Dieses Feature würde idealerweise zwischen M12 (Sync & Sichtbarkeit) und P3 (R3F-Export) liegen. Es dient als "Vorschau" für den vollen Code-Export, indem es die Darstellung bereits auf den Server auslagert.

Für die spätere Sicherheitsprüfung: Erfolgt mit statischer Codeanalyse und gegen bekannte Ausbruchsvektoren gepentestet durch AI. Idee:





### Der AST-Validator im Detail



`validateAiCode.ts` parst den KI-Code mit **acorn** als Abstract Syntax Tree und prüft auf bekannte Escape-Vektoren. Wird ein Verstoß erkannt, wird die Ausführung verweigert und die Fehlermeldung an die KI zurückgegeben – die KI kann dann korrigierten Code senden.



**Drei Blocklisten:**



| Liste | Was sie blockiert | Beispiele |

| --------------------------- | ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |

| **Blockierte Knoten-Typen** | Sprachkonstrukte, die den Scope umgehen | `ThisExpression` (→ window), `ImportExpression`, `MetaProperty`, `WithStatement`, `TaggedTemplateExpression` |

| **Blockierte Identifier** | Variablennamen, die auf Globals verweisen | `window`, `document`, `globalThis`, `eval`, `Function`, `arguments`, `fetch`, `Proxy`, `Reflect`, `localStorage`, etc. |

| **Blockierte Properties** | Property-Zugriffe auf Prototype-Chain | `.constructor`, `.__proto__`, `.prototype`, `.__defineGetter__`, etc.





/**

* validateAiCode.ts – AST-basierter Sicherheitsvalidator für AI-generierten Code

*

* ── Bedrohungsmodell ──────────────────────────────────────────────────────────

*

* Die AI generiert JavaScript-Code, der über `evaluate()` im Browser ausgeführt

* wird. Der Code läuft in einem `with (apiObject) { ... }` Kontext, sodass die

* API-Funktionen als globale Variablen verfügbar sind. Das `with`-Statement

* dient der Ergonomie, NICHT der Sicherheit.

*

* Sicherheit wird ausschließlich durch diesen AST-Validator gewährleistet.

* Er prüft den Code VOR der Ausführung auf bekannte Escape-Vektoren:

*

* 1. `this` → `window` in non-strict mode (ThisExpression)

* 2. `arguments` → callee.constructor chain (Identifier)

* 3. `.constructor` → Function('return this')() (MemberExpression)

* 4. `import()` → dynamischer Module-Import (ImportExpression)

* 5. Globale Objekte → window, document, APP, etc. (Identifier)

* 6. Computed access → obj['constr'+'uctor'] (komplexe MemberExpression)

*

* ── Design-Entscheidungen ─────────────────────────────────────────────────────

*

* • Blocklist statt Allowlist auf Knoten-Ebene: Der AI-Code darf normales JS

* verwenden (Loops, Conditionals, Arrow-Functions, etc.). Nur spezifische

* gefährliche Konstrukte werden blockiert.

*

* • Acorn als Parser: ~35kB, zero Dependencies, parst ~10kB in <1ms.

* Bereits als transitive Webpack-Dependency vorhanden.

*

* • Fehlermeldungen sind so formuliert, dass die AI sie versteht und

* korrigierten Code senden kann.

*

* • Computed MemberExpression: nur numerische Literale und einfache Identifier

* als Key erlaubt. String-Literale werden gegen BLOCKED_PROPERTIES geprüft.

* Alle komplexeren Ausdrücke (BinaryExpression, CallExpression, etc.) werden

* blockiert, da sie zur Obfuscation genutzt werden könnten. |

Das ist ein exzellenter, pragmatischer Architektur-Entwurf. Er adressiert direkt das Risiko 6 (Custom-Feature-Robustheit) aus der vorherigen Roadmap und passt perfekt zur clientseitigen, ressourcenschonenden Philosophie von FieldDraft.

Die Entscheidung, acorn zu nutzen, ist sehr gut (Figma hat in den frühen Versionen seines Plugin-Systems einen ganz ähnlichen AST-basierten Ansatz verfolgt, bevor sie auf einen eigenen C++-Interpreter umgestiegen sind). Besonders deine Regelung für Computed MemberExpressions (obj[expr]) zeigt, dass du die typischen JS-Obfuscation-Tricks (obj['con' + 'structor']) verstanden und präventiv geschlossen hast.

Lass uns diesen Ansatz einem kurzen "Candor-Check" unterziehen, denn JavaScript statisch per Blocklist abzusichern, ist ein berüchtigtes Katz-und-Maus-Spiel. Hier sind ein paar konzeptionelle Reibungspunkte und Ausbruchsvektoren, die dein Validator noch abdecken muss:

1. Der architektonische Konflikt: with vs. Strict Mode
Du schreibst: „Der Code läuft in einem with (apiObject) { ... } Kontext…“
Das Problem: Das with-Statement ist im JS Strict Mode ("use strict";) strikt verboten. Wenn du den Code ohne Strict Mode ausführst, öffnest du Tür und Tor für subtile Ausbrüche (z.B. implizite globale Variablenzuweisungen, wenn ein let vergessen wird, oder unvorhersehbares this-Binding).

Meine Empfehlung: Verzichte auf with. Die Ergonomie lässt sich besser über ein Konstrukt wie new Function(...keys, code)(...values) lösen. Du injizierst die API als Funktionsparameter: new Function('fd', 'ctx', 'id', 'def', userCode). Das erlaubt dir, den Code im Strict Mode laufen zu lassen, was eine ganze Klasse von Ausbrüchen auf Engine-Ebene schließt, bevor der AST-Validator überhaupt anspringt.

2. Versteckte Property-Zugriffe (Die AST-Edge-Cases)
Deine Liste blockiert .constructor als MemberExpression. In modernem JS gibt es aber viele Wege, auf Properties zuzugreifen, die der Validator als AST-Knoten erkennen muss:

Destructuring Assignment (ObjectPattern):

JavaScript
const { constructor } = obj;
// Das ist keine MemberExpression, sondern ein ObjectPattern!
Dein Validator muss Property-Knoten innerhalb von Object/Array-Patterns prüfen.

Object Literals (ObjectExpression):

JavaScript
const malicious = { get __proto__() { return ... } };
Auch hier muss der Key (als Identifier oder Literal im Property-Knoten) gegen die Blockliste geprüft werden.

Template Literals:

JavaScript
obj[`constructor`]
Fällt unter TemplateLiteral. Wenn Computed Properties erlaubt sind (sofern sie nur String-Literale enthalten), musst du auch Template Literals prüfen, sofern sie keine Expressions (${...}) enthalten (oder Letztere komplett in MemberExpressions verbieten).

3. Shadowing von erlaubten Parametern
Wenn du blockierte Identifier wie eval oder window suchst, musst du bedenken, dass JS Shadowing erlaubt. Was passiert, wenn die KI folgenden, eigentlich harmlosen Code schreibt?

JavaScript
const window = 10;
fd.extrude(..., { depth: window });
Wenn dein AST-Validator stumpf nach dem Identifier-Namen window sucht, blockiert er das, obwohl es eine ungefährliche lokale Variable ist.

Lösung für den MVP: Einfach stumpf den String blockieren. Es ist für eine KI völlig zumutbar, gesagt zu bekommen: "Verwende niemals den Variablennamen 'window', auch nicht lokal." Das spart dir einen komplexen Scope-Analyzer im AST-Traversal.

4. Das Endlos-Schleifen-Problem (Denial of Service)
Statische AST-Analyse schützt hervorragend vor Scope-Escapes (Datenklau, Manipulation des Host-DOMs). Sie schützt aber nicht vor DoS (Denial of Service):

JavaScript
while(true) {}
Da der Code synchron in deinem Web Worker läuft (oder auf dem Main Thread), hängt sich dieser komplett auf. Ein try/catch hilft hier nicht.

Ergänzung für dein Design: Du hast den AST ohnehin schon geparst. Du kannst (wie es z.B. p5.js oder Codepen machen) den AST vor dem Ausführen modifizieren (AST Rewriting). Du fügst am Ende jedes Loop-Knotens (WhileStatement, ForStatement) einen Check ein:

JavaScript
if (Date.now() - _loopStart > 1000) throw new Error("Timeout");
Das ist zwar etwas aufwändiger als reine Validierung, macht das System aber extrem robust gegen "dumme" KI-Fehler.

Zusammenfassung für dein Design-Dokument
Deine Grundidee ist absolut tragfähig und der richtige Weg für Phase 2+. Ich würde den Plan im Konzept wie folgt nachschärfen:

Strict Mode ist Pflicht: Ausführung via new Function('fd', ...) statt with.

Strikte Computed Properties: obj[expr] blockiert alle expr, die keine reinen String/Number-Literale sind. Template Strings in Computed Properties werden blockiert.

Destructuring-Prüfung: ObjectPattern-Knoten werden in die Prüfung aufgenommen, um Destructuring-Escapes zu verhindern.

Dumb Blacklisting: Variablennamen aus der Blockliste sind auch als lokale Variablen verboten (kein Scope-Tracking nötig).

Mit diesem AST-Validator und der Feedback-Schleife an die KI hast du ein System, das sich selbst repariert, wenn es zu "kreativ" wird!

Genau: kein "with" (Artefakt, weil ich dir einfach die Beschreibung eines älteren Codes aus ähnlichem Projekt gezeigt habe).

Die finale Architektur für den Validator nutzt new Function('fd', 'ctx', 'id', 'def', '"use strict";\n' + userCode) kombiniert mit der gehärteten Acorn-AST-Blockliste.

Die aktualisierten Kernregeln für validateAiCode.ts lauten:

Strict Mode Enforcement: Die Einbettung in new Function mit explizitem "use strict"; schließt das this-Binding auf das globale Objekt (window) auf Engine-Ebene aus.

Erweiterte AST-Blockliste (Node-Typen): * ImportExpression (Dynamische Imports)

MetaProperty (z. B. new.target)

TaggedTemplateExpression

ObjectPattern / ArrayPattern (Schutz vor Destructuring-Escapes wie const { constructor } = obj;)

Computed MemberExpressions: Nur Literal-Knoten (Strings/Numbers) sind als Keys in obj[expr] erlaubt. TemplateLiteral-Knoten werden blockiert. Jeder String-Literal-Key wird gegen die Liste verbotener Properties (z. B. constructor, __proto__) geprüft.

Dumb Blacklisting für Identifier: Isolierte Identifikatoren wie window, document, eval oder fetch werden global verboten, unabhängig von ihrem Scope (keine Ausnahmen für lokales Shadowing).

DoS-Protection (AST-Rewriting): Loop-Knoten (WhileStatement, ForStatement) erhalten einen injizierten Timestamp-Check, der bei Ausführungszeiten >1000ms einen Timeout-Error wirft.

Das System übergibt erkannte Regelverstöße im Validierungsschritt direkt als formatierten Fehler an die KI zurück, bevor die JavaScript-Engine den Code kompiliert.
